# 同次构建的软件包仓库

新版工作流额外交付 `rax3000m-emmc-matching-packages-<run_id>`。
它包含这次镜像实际安装的 APK、签名索引 `packages.adb`、公开验证密钥、
SHA256SUMS 和 `package-repository-check.json`，供离线维护或恢复同版本软件包。
没有为此选择全软件包、其他设备、SDK 或 ImageBuilder；只保存已编译的安装包。

构建使用 OpenWrt 原生自动生成的临时签名密钥，不依赖个人密钥或私有服务器。
本设备的 `apk-package-signing.patch` 在原生 `apk mkpkg` 阶段为每个 APK 签名，
仓库索引也使用同一密钥签名。公开密钥已随该次镜像安装到 `/etc/apk/keys/`。
私钥留在临时构建树，不进入固件、软件包附件或诊断附件。

## 构建验收

每个已安装软件包都必须在本次构建的 APK 集合中找到唯一对应项。
检查名称、版本、架构、依赖及原生索引中的内容身份与镜像已安装数据库一致，
所有内核依赖必须指向镜像真实的完整 kernel ABI。
使用镜像已有信任公钥运行原生 `apk verify`，验证所有 APK 和索引。
随后以空数据库、仅使用这个本地仓库运行原生离线依赖求解，结果必须复现最终包清单。
这些检查不运行软件包脚本或任何目标程序，也不下载代理核心。
任何失败均阻止候选和软件包发布，不使用强装、覆盖或关闭签名的参数。

## 手动使用

先确认软件包附件与正在使用的固件来自同一次 Actions 运行，
且 `package-repository-check.json` 的 `image_sha256` 对应已刷固件的校验值。
不同运行通常有不同构建密钥，不能仅凭相同 25.12.5 标签混用。
无需导入其他运行的公钥；当前固件已经信任它自己的同次构建公钥。

把整个软件包附件解压到自己选定的存储目录后，在该目录中手动检查：

```sh
sha256sum -c SHA256SUMS
apk verify packages.adb ./*.apk
```

校验值检查文件完整性，`apk verify` 另行检查当前系统信任的签名。
私密保存自己修改过的配置，并先模拟所需软件包的安装：

```sh
apk --no-network --repositories-file /dev/null \
  --repository "file://$(pwd)/packages.adb" \
  add --simulate luci-app-openclash=0.48.002-r9
```

这个命令仅使用本地索引并模拟求解；不修改长期软件源，也不安装软件包。
确需恢复同版本软件包时，再依据具体故障选择操作，不必重装整套现有软件。
仓库只包含本次已编译的包；需要新增内核模块时，在固定配置中加入它并重新构建匹配固件。
系统升级使用经过审核的 sysupgrade 镜像，不以全量 `apk upgrade` 代替系统升级。
软件包仓库验证不代表引导兼容性或真机稳定性已验证。
